DING Golf: Detecting a Full Attack Chain with a SIEM

My Fullstack Academy capstone: I built an isolated four-VM lab, ran a realistic phishing-to-ransomware attack against a fictional company end to end, and — the real point of the project — detected every stage of it with 18 custom Wazuh rules and a live SOC dashboard.

Overview

The goal of this capstone was to understand an attack well enough to catch it. Rather than study one stage in isolation, I built the whole kill chain against a fictional company, DING Golf, so I could see exactly what each attacker action looks like in the logs — and then write detections that fire on it.

The scenario: a customer-service employee is phished, her reused password is validated against an internal server, the attacker moves laterally over SMB to pull "confidential" files, and a simulated ransomware step renames demo files and drops a ransom note. A Wazuh SIEM watches both Windows machines the entire time.

What makes it a blue-team project: the attack is the setup. The deliverable is 18 custom detection rules, File Integrity Monitoring on sensitive folders, a 9-panel dashboard, and a filtered SOC alert queue that surfaces the critical events.

It's a solo expansion of an earlier team bootcamp project (a hospital ransomware simulation), rebuilt here with a more polished phishing portal, SMB-based lateral movement, and detection coverage across every phase.

Scope & ethics

Everything ran on an isolated host-only network (192.168.56.0/24) with no route to the internet or any real system. The company, the employee "Sarah Chen," all credentials, and all "confidential" files are entirely fictional and were created for this lab. Nothing here targets a real person or organization, and this write-up documents the methodology and the detections, not a reusable toolkit.

To make the attack visible, I configured the Windows side the way a monitored environment would be: static IPs and meaningful hostnames, SMB shares for the lateral-movement target, and — most importantly — auditing turned up. I enabled Logon, File Share, Detailed File Share, File System, Process Creation, and Filtering Platform policies, and set SACLs on the monitored folders so Windows emits Event ID 4663 on access. I also removed the default event exclusions from the Wazuh agent config so 4663, 5145, and related events actually reached the SIEM.

The attack chain

Each stage was built to generate a distinct, detectable footprint:

  1. Phishing

    A custom portal served from Kali imitates a webmail inbox and a branded login page. "Sarah" opens it, clicks through, and submits her credentials, which are logged on the attacker host. Signal: a credential-submission event from the phishing portal.

  2. Credential capture & auto-trigger

    A watcher script monitors the credential log and kicks off the rest of the chain the moment a submission lands, so the whole scenario runs hands-off for a clean demo.

  3. Network reconnaissance

    From the attacker's view, host and service discovery locate the server and confirm SMB is open.

    nbtscan 192.168.56.0/24
nmap -sV -p 445 192.168.56.109
  4. Credential validation

    The phished password is checked against the server over SMB — the "valid accounts" reuse step (crackmapexec), which on the server side looks like a network logon.

  5. Lateral movement & exfiltration

    Using the validated credentials, the attacker browses an SMB share and copies "confidential" demo files. Signal: remote share access and file reads right after the suspicious logon.

  6. Ransomware simulation

    A script renames demo files to .locked on both VMs and drops a ransom note. No real encryption and no real data — the point is the file-change pattern FIM sees.

Detection engineering — the core of the project

I wrote 18 custom Wazuh rules mapping to every phase, enrolled both Windows hosts as agents in a shared CYBERLAB group, and turned on real-time File Integrity Monitoring (60-second scan plus realtime change detection) over the confidential folders. A selection of the rules:

RuleLevelFires onChain stage
10112Credentials submitted to the phishing portalPhishing
1024SMB network logon detectedValidation
1001018Remote SMB share access on the serverLateral movement
10412File access after a suspicious SMB logonExfiltration
11010SMB brute force — 5 failed logons in 60sValidation
11210After-hours SMB logon (11pm–6am)Lateral movement
10615.locked file rename detected (FIM)Ransomware
10715Ransom note dropped (FIM)Ransomware
11315Mass file encryption in progressRansomware
10815Full attack chain confirmed (correlated)Impact

The rules escalate the way an analyst would want them to: a single SMB logon is informational (level 4), file access after a suspicious logon is a real lead (12), and the file-rename and ransom-note FIM events are critical (15). Rule 108 is a correlation rule — it only fires once the earlier stages have been seen together, which is what turns a pile of alerts into "this is one incident."

Two views made it usable as a SOC would use it:

  • DING Golf Security Monitor — a 9-panel dashboard showing alerts by severity, by agent, by rule, and over time, so the whole chain is visible at a glance as it unfolds.
  • Operation DING SOC Queue — a saved search filtered to high-severity alerts only, so the critical events aren't buried in logon noise.

Takeaways

  • Detection depends on telemetry. The hardest part wasn't writing rules, it was making Windows emit the right events — SACL auditing for 4663 and removing Wazuh's default exclusions. No log, no detection.
  • Correlation beats volume. Any one event here is ambiguous. The high-confidence alert is the sequence: phish → logon → file access → mass rename.
  • FIM is the ransomware backstop. When prevention fails, a flood of .locked renames is an unmistakable, high-severity signal.
  • Building the attack made me a better defender. Seeing each stage from the attacker's side is what let me write detections that fire on the behavior, not just on a specific IP or filename.

This project ties together the individual skills from my labs — the SIEM and detection work, Windows event analysis, and SMB/networking — into one end-to-end incident. It's the work I'm most proud of.
