Microsoft Sentinel & KQL

I used Microsoft Sentinel's Log Analytics workspace to investigate authentication activity with KQL, then turned the query into an analytics rule and worked the incident it generated.

Walkthrough

  1. Explore the table

    Start small, look at the schema, then filter.

    SecurityEvent
| where TimeGenerated > ago(24h)
| take 20
  2. Summarize failed logons

    summarize with bin() buckets the failures per hour by account and source.

    SecurityEvent
| where TimeGenerated > ago(24h) and EventID == 4625
| summarize FailedAttempts = count() by Account, IpAddress, bin(TimeGenerated, 1h)
| order by FailedAttempts desc
  3. Correlate: did a noisy IP ever succeed?

    A let statement builds the suspect list, then a join against successful logons (4624) finds any overlap.

    let suspects = SecurityEvent
    | where TimeGenerated > ago(1d) and EventID == 4625
    | summarize Failures = count() by IpAddress
    | where Failures > 10;
SecurityEvent
| where TimeGenerated > ago(1d) and EventID == 4624
| join kind=inner suspects on IpAddress
| project TimeGenerated, Account, Computer, IpAddress, LogonType, Failures
  4. Create an analytics rule

    Analytics → Create → Scheduled query rule: the correlation query, run every hour over the last day, alert when results > 0, and map Account and IP entities so incidents link together.

  5. Work the incident

    From Incidents: assign it to myself, set the status to Active, open the investigation graph to see the related entities, add comments with findings, and close with a classification (true positive, benign positive, or false positive).

KQL vs. SPL

Having used both, the concepts map closely:

TaskKQL (Sentinel)SPL (Splunk)
Filterwheresearch / where
Aggregatesummarize count() bystats count by
Time bucketsbin(TimeGenerated, 1h)bin _time span=1h / timechart
Pick columnsprojecttable / fields
Joinjoin kind=innerjoin (or stats by shared field)

Key takeaways

  • Entity mapping is what makes Sentinel incidents useful. Without it, alerts don't correlate.
  • Always bound queries with TimeGenerated, for speed and cost.
  • The closing classification feeds back into tuning, so false positives should be labeled honestly.
