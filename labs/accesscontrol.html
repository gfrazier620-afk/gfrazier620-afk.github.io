Access Control & Least Privilege

Most breaches get worse because accounts had more access than they needed. I built a small role-based permission model on both Windows and Linux, then tested it from each user's point of view.

Windows: role-based NTFS permissions

  1. Create users and a role group
    New-LocalGroup -Name "Finance"
New-LocalUser -Name "jdoe" -Password (Read-Host -AsSecureString)
Add-LocalGroupMember -Group "Finance" -Member "jdoe"
  2. Lock the folder to the role

    Remove inherited permissions, then grant Modify to Finance only. (OI)(CI) applies it to files and subfolders.

    icacls C:\Finance /inheritance:r
icacls C:\Finance /grant "Administrators:(OI)(CI)F" "Finance:(OI)(CI)M"
icacls C:\Finance
  3. Verify as each user

    Signed in as a Finance member (access works) and a non-member (access denied).

Linux: group permissions

  1. Group, ownership, and mode

    2770 sets the setgid bit, so new files inherit the finance group, and gives no access to others.

    sudo groupadd finance
sudo usermod -aG finance jdoe
sudo mkdir /srv/finance
sudo chown root:finance /srv/finance
sudo chmod 2770 /srv/finance
  2. Test from both sides
    sudo -u jdoe touch /srv/finance/report.txt     # allowed
sudo -u guest ls /srv/finance                  # Permission denied

Auditing access changes

Changes to group membership are security events worth alerting on:

Event IDMeaning
4732Member added to a security-enabled local group
4728Member added to a security-enabled global group (domain)
4663Object access attempt (requires auditing on the folder)

Key takeaways

  • Assign permissions to groups, never to individual users. It's the only way access reviews stay manageable.
  • Always test access as the user, not as the admin who configured it.
