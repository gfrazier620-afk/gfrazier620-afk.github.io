Detecting Brute-Force Logons in a SIEM

A host is generating a burst of failed Windows logons. I worked the alert the way a Tier 1 analyst would: confirm it, find the source, check whether the attacker got in, and turn the search into a repeatable detection.

  • SIEM
  • Splunk
  • Windows logs
  • T1110
Environment
Windows Server logs forwarded to Splunk
Tools
Splunk SPL, Event Viewer
Focus
Authentication monitoring
ATT&CK
T1110 Brute Force

  1. Scenario

Scenario

The SOC dashboard shows a jump in failed logons against a Windows server. The questions to answer: Is it an attack? Where is it coming from? Did anything succeed?

The Windows Security events that matter for this investigation:

Event IDMeaningWhy it matters
4625An account failed to log onThe volume and pattern show the attack
4624An account successfully logged onA success after many failures is the critical signal
4740A user account was locked outConfirms the lockout policy triggered
4672Special privileges assigned to new logonShows whether an admin-level account was used

Walkthrough

  1. Baseline failed logons over time

    A timechart shows whether this is normal noise or a spike.

    index=wineventlog EventCode=4625
| timechart span=5m count AS failed_logons
  2. Pivot on the source

    Group by source IP to see who is generating the failures and which accounts they target.

    index=wineventlog EventCode=4625
| stats count AS failures dc(Account_Name) AS accounts_tried
        values(Account_Name) AS accounts BY Source_Network_Address
| sort - failures
  3. Classify the pattern

    One IP trying many accounts with a few attempts each is password spraying (T1110.003). One IP hammering one account is classic brute force (T1110.001). Logon Type 3 (network) or 10 (RDP) shows the access path.

  4. Check for a successful logon from the same source

    This step decides the severity. A 4624 from the attacking IP turns a blocked attempt into a possible compromise.

    index=wineventlog (EventCode=4625 OR EventCode=4624)
    Source_Network_Address="203.0.113.45"
| sort _time
| table _time EventCode Account_Name Logon_Type ComputerName
  5. Turn it into a detection

    I saved the logic as a scheduled alert that runs every 10 minutes and fires when one source exceeds a threshold.

    index=wineventlog EventCode=4625 earliest=-10m
| stats count AS failures dc(Account_Name) AS accounts BY Source_Network_Address
| where failures > 10 OR accounts > 5
  6. Document and hand off

    I recorded the source IP, targeted accounts, time window, whether any logon succeeded, and a recommendation: block the IP at the firewall, reset any account that had a success, and confirm the lockout policy.

Key takeaways

  • Volume alone isn't the finding. A success after failures is what escalates an alert.
  • dc() (distinct count) separates spraying from brute force in one search.
  • Thresholds need tuning against a baseline, or the rule floods the queue with false positives.
  • I applied the same pattern hands-on in my SSH honeypot project.
